01 / The perspective

Beyond a pass or fail.

Testing a model means understanding not just whether it broke, but how and why.

When the output looks convincing, the details matter most.

I design adversarial inputs, compare competing outputs, and inspect the failures a surface-level score can miss. Where confidentiality limits what can be shared, the work below focuses on methods rather than client names or private results.

02 / Selected work

A closer look
at the work.

Three areas of practice, connected by the same question: what does the model miss?

01   /   Adversarial evaluation
CASE STUDY 01

Red teaming language models.

Developed prompts that probe weaknesses in retrieval and reasoning, including hard-to-find sources, historical clippings, PDFs, and information embedded in tables. The aim was to expose confident answers built on weak evidence, not simply to collect failed responses.

FOCUS Prompt design · Source verification · Failure analysis

02   /   Multimodal testing
CASE STUDY 02

Testing what models see.

Explored how phrasing could confuse model descriptions of body parts in 3D medical imagery. In separate image-generation tests, used rhyming prompts and layered spatial and color constraints to surface errors in object placement, counts, lettering, and scene relationships.

FOCUS Medical-imaging prompts · Visual consistency · Hallucination review

03   /   Evaluation tooling
CASE STUDY 03

Tools for clearer comparisons.

Built private tools to compare outputs from different models across text, images, apps, and code. Each run starts without prior conversational context; the tools help flag areas to inspect, while a human reviewer checks the actual output and whether the resulting application works.

FOCUS Side-by-side review · Isolated runs · Human-in-the-loop checks

03 / The method

The method is
the differentiator.

Repeatable rigor, without mistaking a polished response for a correct one.

I / DESIGN

Probe the edge.

Start with a real question about behavior. Design prompts that stress a specific capability rather than piling on arbitrary difficulty.

II / COMPARE

Keep runs clean.

Evaluate model outputs side by side, clearing conversational context between runs so previous answers do not contaminate the next comparison.

III / VERIFY

Inspect the evidence.

Use tools to narrow the search, then verify sources, visual details, code behavior, and failure claims with human judgment.
